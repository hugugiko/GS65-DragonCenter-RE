# Reverse-Engineering Artifact Inventory

**English** | [简体中文](../zh/03-artifacts.md)

This page describes the local analysis artifacts that were produced while studying
Dragon Center, and explains why the raw artifacts are **intentionally not included** in
this repository.

---

## 1. What the artifacts are

The analysis produced three kinds of intermediate files, all generated locally from a
legally owned copy of the software:

| Artifact | Generated by | Content |
|---|---|---|
| `*.txt` (e.g. `MSIAPService.exe.txt`) | `tools/dump_dotnet.py` | .NET metadata: type definitions, fields and constants, method definitions, P/Invoke imports, type references, user strings |
| `*.str.txt` (e.g. `Dragon Center.exe.str.txt`) | `tools/strings_extract.py` | ASCII and UTF-16LE strings extracted from a PE binary |
| `*_il.txt` (e.g. `fan_il.txt`, `batt_il.txt`) | `tools/il_dump.py` | IL disassembly of methods whose full name matches a filter string |

Specific files that were studied:

| File | Assemblies / methods of interest |
|---|---|
| `MSIAPService.exe.txt` / `.str.txt` | Service-side types: `WinIO`, `WMI`, `NativeNamedPipeServer`, `EncrptyDecrypt`; pipe name, command prefixes, JSON keys, crypto clues |
| `MSIECO.dll.txt` / `eco_il.txt` | ECO mode enums and power-scheme switching methods |
| `Dragon Center.exe.txt` / `.str.txt` | Client types such as `FanSettings`, `BatteryUI`, `SCM`, `WinAndFnChange`; WMI classes and WQL queries |
| `WMILib.dll.str.txt` | Native WMI COM wrapper exports `ReadWMI`, `ReadWMIAll`, `WriteWMI` |
| `MsiHid.dll.str.txt`, `UEFIVaribleDll.dll.str.txt` | HID and UEFI variable access (not needed for fan/battery/mode) |
| `ProfileHelperModel.dll.txt` / `.str.txt` | User profile data model |
| `WinIo64.dll.str.txt` | WinIo driver exports and port-I/O entry points |
| Other `.exe.txt` / `.str.txt` files | `CommandCenter_Start`, `GameCenter-OC`, `gpuControl`, `MSIAPService` |
| `fan_il.txt`, `batt_il.txt`, `wafc_il.txt`, `scm_il.txt`, `winio_il.txt`, `enc_il.txt` | Targeted IL disassembly of fan, battery, WMI/ACPI, system-control, WinIo, and encryption methods |

## 2. Why the raw artifacts are not published

These files are **derived reproductions of a proprietary program**. A metadata dump
reproduces the program's type and method structure; a string dump reproduces its embedded
string resources; an IL dump reproduces its executable logic. Publishing them would
redistribute a substantial part of MSI's copyrighted work and could also conflict with
the software's EULA.

They are also unnecessary for the purpose of this repository. What matters for
interoperability is the small set of functional facts extracted from them, which are
documented in:

- [01-architecture.md](01-architecture.md) — architecture, protocol, WMI classes, power-plan GUIDs;
- [02-ec-register-map.md](02-ec-register-map.md) — the calibrated EC offsets.

The helper **scripts** under [`tools/`](../../tools/) are original work and are
published under the MIT License. They contain no MSI data.

## 3. Reproducing the artifacts

If you own a copy of the software, you can regenerate the artifacts for your own
research:

```bash
pip install dnfile dncil pefile

python tools/dump_dotnet.py "path/to/Assembly.exe"
python tools/strings_extract.py "path/to/Assembly.exe"
python tools/il_dump.py "path/to/Assembly.exe" "FanSettings" fan_il.txt
```

The first two scripts write output to the current directory; `il_dump.py` writes to the
path you pass. Treat those outputs as proprietary material:

- do not commit them to this repository or any public repository;
- do not paste large excerpts into issues or pull requests;
- summarize only the functional facts, as this repository does.

The `.gitignore` already excludes executable files, drivers, `.eps` hives, `.bin` dumps,
and `*.str.txt` / IL output to reduce the chance of accidental publication.
